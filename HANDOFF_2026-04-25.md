Alan asked to investigate how two competing Israeli rental sites (`4kirot.com`, `ho-me.app`) source their Facebook data, with an eye to learning whether PDIS is overpaying for Apify or missing a better architectural pattern.

**Findings from live reverse-engineering of ho-me.app:**
- Frontend: React + Vite on Vercel, single ~560KB bundle
- Backend: None of their own — browser queries Supabase REST directly at `jdawkqdjjgnnfqmicgfh.supabase.co/rest/v1/processed_apartments`
- One flat table schema: `id, price, rooms, city, neighborhood, image_url_1, images, has_mamad, has_parking, has_balcony, has_elevator, pets_allowed, is_brokerage, floor, sqm, lease_type, entry_date, renovation_level, ai_summary, post_url, created_at`
- Image filenames like `4302566929995229_1.jpg` = `{fb_post_id}_{index}.jpg` — this is the **default output format of Apify's `apify/facebook-groups-scraper`**. They almost certainly use the same actor as PDIS.
- Post URLs resolve to standard public FB group permalinks
- Indie operator: `@home_isreal` Instagram (note the typo "isreal"), gmail contact (`home.alerts.info@gmail.com`), © 2026 HoMe

**4kirot.com:** same concept — their own terms acknowledge aggregating from "various sources on the internet (such as Facebook, bulletin boards, etc.)". Email/password + Google login, no Facebook OAuth — they scrape server-side using their own cookies, same as any other FB scraper would.

**Conclusion:** neither site has a secret tech advantage over PDIS. They run the same pipeline (Apify or equivalent scraper → LLM parse → DB → display) with more UI polish and higher scan cadence (4×/day vs PDIS's 1×).
